# 版本迭代与自动更新

这份文档回答三件事：**版本号怎么定**、**每次发布怎么出包**、**用户手上的旧版本怎么自己升上来**。

目标形态：在 GitHub 上打一个 `v0.2.0` 的 tag，几分钟后仓库 Release 里出现签名且公证过的安装包，官网上的下载按钮指向最新版，而已经装了旧版本的用户在菜单栏里点「检查更新…」就能拿到它。

---

## 零、先说清楚两条硬约束

这两条决定了整套方案为什么只能长这样，别的写法都会在某个环节炸掉。

**1. 屏幕录制权限是绑在代码签名上的。**
macOS 按 Team ID 记这个授权。当前仓库默认走 ad-hoc 签名（`-`），每次重编都换一套签名，于是权限被反复索要，旧授权还得手动删（README 里已经写过）。所以：

> 发布出去的包必须是 **Developer ID Application** 签名 + Apple 公证（notarize）+ stapled。
> 否则「自动更新」每更新一次就等于让用户重新授权一次屏幕录制，这是最坏的用户体验。

**2. 本 app 是 `LSUIElement`（无 Dock 图标）+ `LSMultipleInstancesProhibited`。**
它平时不出现在 Dock，也不允许开第二个实例。所以更新器的安装阶段必须**先退出当前进程再替换**——不能指望用户自己去 `/Applications` 里拖。Sparkle 的 `SUUpdater` 正是这么做的（由 Sparkle 的 XPC 安装器接管），自己写一个替换器要重新踩一遍这些坑，不划算。

---

## 一、版本号策略

采用 **SemVer**，并把「给人看的版本」和「给系统看的版本」分开：

| Info.plist 键 | 来源 | 例子 | 说明 |
|---|---|---|---|
| `CFBundleShortVersionString` | git tag | `0.2.0` | 市场版本，显示在「关于」页 |
| `CFBundleVersion` | CI 构建号（单调递增整数） | `42` | 系统/更新器用来判大小，只增不减 |

规则：

- **唯一来源是 git tag。** 仓库里的 `Resources/Info.plist` 保持占位值（`0.1.0` / `1`），CI 在打包前用脚本注入真实值（`Scripts/stamp-version.sh`）。这样不会出现「tag 是 0.3.0、包里写着 0.2.9」这类对不上的情况。
- tag 格式 `v<MAJOR>.<MINOR>.<PATCH>`，只有这个格式会触发发布流水线。
- 预发布用 `v0.3.0-rc.1`，打出来的 Release 标记为 **pre-release**，并且**不写进稳定通道的 appcast**（见第五节）。
- PATCH 只修 bug、不动行为；MINOR 加功能；MAJOR 改掉不兼容的行为或最低系统版本。

## 二、分支与发布节奏

```
feature/xxx  ──PR──▶  main  ──tag v0.2.0──▶  Release（自动出包）
```

- `main` 永远处于「可以打 tag 发布」的状态。CI 挂了就不许合。
- 功能一律走分支 + PR，PR 上必须绿：`swift build` + `swift test`。
- 发布步骤（人工只做前三步）：

  1. 更新 `CHANGELOG.md`；
  2. `git tag v0.2.0 && git push origin v0.2.0`；
  3. 流水线跑完，Release 以 **draft** 形态出现 → 人工在装了旧版本的机器上验证一次「检查更新」能升上来 → 点 Publish；
  4. 官网下载按钮读的是 GitHub Releases 的 latest，无需改动。

## 三、自动更新：选型结论

三条路都看过，结论是 **Sparkle 2**。

| 方案 | 优点 | 致命问题 |
|---|---|---|
| **Sparkle 2**（选它） | 事实标准；edDSA 签名校验；支持 delta 增量更新；自带 XPC 安装器，能退出进程后替换自身；支持「关键更新」强制升级、预发布通道 | 引入一个二进制依赖（SPM 即可） |
| 自制检查器 | 无依赖，几十行：拉 GitHub Releases 的 latest tag 比对，跳到下载页 | 只能「告诉用户有新版本」，不能替他装；自己实现下载/校验/替换/提权是重复造 Sparkle，且容易在权限与 Gatekeeper 上翻车 |
| Homebrew cask | 分发渠道好 | 不是更新器，且要求用户装了 brew |

Sparkle 集成要点（落到代码时照这个做）：

1. Package.swift 加依赖
   ```swift
   .package(url: "https://github.com/sparkle-project/Sparkle", from: "2.6.0")
   ```
   并给 `PrivacyWindow` executable target 加上 `Sparkle`。
2. `Info.plist` 加三个键：
   - `SUFeedURL`：`https://<官网域名>/appcast.xml`
   - `SUPublicEDKey`：edDSA 公钥（用 Sparkle 的 `generate_keys` 生成，私钥进 GitHub Secrets）
   - `SUEnableAutomaticChecks`：不写死，改为首次启动时在设置里询问一次
3. 菜单栏加一项「检查更新…」，设置窗口「通用」页显示「自动检查更新」开关与上次检查时间。
4. appcast 由 CI 用 Sparkle 的 `generate_appcast` 生成——它同时算出 zip 的 edDSA 签名和 delta 补丁，不要手写这个 XML。

**过渡方案（M3 之前）**：站点下载页 + 一个只读版本检查（请求 GitHub Releases API，只比对、只提示、不自动装）。这样在 Sparkle 接进来之前也有「有新版本」的通道。

## 四、CI/CD 设计

两条工作流，都在 `.github/workflows/`（本仓库已落地）：

### `ci.yml` — 每次 push / PR

`macos-15` runner，Xcode 16（Swift 6）：

```yaml
swift build -c release
swift test
```

只做编译和单测，不签名、不出包。跑得快，是合并的门槛。

### `release.yml` — 推 tag `v*` 时

```
1. 解析 tag → MARKETING_VERSION / BUILD_NUMBER
2. Scripts/stamp-version.sh 注入 Info.plist
3. swift build -c release --arch arm64 --arch x86_64   （通用二进制）
4. ./build.sh 组装 .app 并 codesign（Developer ID Application）
5. zip → notarytool 提交公证 → stapler staple → 再校验一次签名
6. （可选）打 dmg 给手动下载的用户
7. 下载 Sparkle 的 generate_appcast → 生成/合并 appcast.xml（用 SPARKLE_ED_PRIVATE_KEY 签名）
8. 上传 zip / dmg / appcast.xml 到 Release（draft）
9. 把 appcast.xml 同步到官网静态目录，随 Pages 一起发布
```

**feed 托管在官网站点根目录**（`/appcast.xml`），而不是 Release 的资源直链。原因：Release 资源的 URL 里带着版本号，会随每次发布变化；而 `SUFeedURL` 写死在已经发出去的包里，必须是永久地址。

### 需要的仓库 Secrets

| Secret | 用途 |
|---|---|
| `DEVELOPER_ID_APPLICATION` | 证书名，如 `Developer ID Application: Your Name (TEAMID)` |
| `DEVELOPER_ID_P12_BASE64` + `DEVELOPER_ID_P12_PASSWORD` | 把证书导入 CI 的临时钥匙串 |
| `APPLE_ID` / `APPLE_TEAM_ID` / `APPLE_APP_PASSWORD` | notarytool 公证（App Store Connect 专属密码） |
| `SPARKLE_ED_PRIVATE_KEY` | 给 appcast 签名（`generate_keys` 产出的私钥） |
| `GITHUB_TOKEN` | 仓库自带，用于上传 Release 资源 |

> 没有这些 Secret 时流水线会在签名那一步失败——这是**有意的**：不签名就不许发布（回到第零节第 1 条）。

## 五、通道、灰度与回滚

- **稳定通道**：`appcast.xml`，只包含正式 tag 打出来的包。
- **预发布通道**：`appcast-prerelease.xml`。用户在设置里勾选「接收测试版」才去读它。`rc` tag 只进这个通道。
- **关键更新**：某个版本有严重问题（比如某个 macOS 版本上覆盖层卡住），在 appcast 条目上加 `<sparkle:criticalUpdate>`，Sparkle 会把它标成必须升级。
- **回滚**：每个版本的 zip 都留在 Release 里不删，appcast 只追加不删条目。出问题的版本不撤，而是**发一个更高的 hotfix 版本号 + critical 标记**，让所有人升上去。撤回已发布的包只会让用户卡在坏版本上。
- **降级保护**：`CFBundleVersion` 只允许增大；更新器不会把用户装回旧版本。
- **feed 不可用**：解析失败、网络失败一律静默跳过并延后重试，绝不能阻塞启动或弹错误——这是个菜单栏小工具，不是需要联网才能用的东西。

## 八、发布前检查清单

- [ ] `swift test` 全绿（当前 68 个用例）
- [ ] tag 与 `CHANGELOG.md` 一致，且 tag 已推送
- [ ] Release 里的 zip 能被 `spctl -a -vv` 判为 accepted（公证生效）
- [ ] 在一台**装了上一个版本**的机器上点「检查更新…」，能升上来且升上来后效果正常
- [ ] 升级后**屏幕录制权限没有被重置**（Team ID 没变）
- [ ] 官网下载按钮指向最新 Release
